# 截止前调试操作指南（2026-11-03）

材料截止：**2026-11-04 18:00（北京时间）**。本文按2026-11-03本机实际源码编写；读过README、CONTRIBUTING与交接说明，也只读对照了队友Pi程序。这里只准备操作步骤，没有连接设备、烧录或发送运动命令。

## 0. 先把版本和当前缺口说清楚

**FPGA现在还有一个必须先处理的门槛：最新候选布线完成，但完整时序没有通过。** `lidar-20261103/vision_robot_lidar_20261103_NOT_TIMING_CLOSED.fs`不是可直接验收的交付固件。最终控制47.064/50MHz、GMII108.762/125MHz、LCD42.486/45MHz，且有真实DDR hold与复位问题。9组HDL动态回归通过，不能替代时序或上车验证。原`impl/`也不等于这个候选。详见[构建与修复证据](雷达避障诊断与起点连接_20261103.md)。

下面的“新诊断、双地图、起点连接”步骤，适用于之后确认可用的对应FPGA版本；**不能拿旧R7位流运行操作10，再把不支持协议解释为雷达故障**。目前没有可声称已经完整时序闭合的新版本。你可以先完成Pi联网、识别观察和已有功能素材采集，FPGA时序整改与这些工作分开进行。

这一轮先固定参数：速度环P30/I1/D0；NAV基础速度30 COUNT/10ms；最终软件接受范围双轴5mm。XY导航不调用轮位置PID，这轮不要靠乱调位置环解决雷达拒行。5mm是程序条件，不是实测绝对定位精度；地图仍为64mm/格。

今晚只盯三件事：Pi网页看到带框画面；FPGA拒行有明确原因和记录；合格固件上先完成一条300mm短导航。先人脸，后小狗；先云台单独跟踪，后寻找和接近。

## 1. 接线安排：Pi不用在电脑和FPGA之间来回换网线

```text
USB摄像头 → 香橙派
香橙派eth0（192.168.10.3）──网线──FPGA（192.168.10.2）
香橙派Wi-Fi ──同一Wi-Fi/热点──电脑：SSH隧道看识别画面
电脑 ──原蓝牙串口/VOFA──FPGA：任务命令或诊断采集
```

电脑和Pi无线网段沿用路由器/热点分配的地址，**不用改成192.168.10.x**；Pi有线192.168.10.3/24保持原配置。本流程要求Wi-Fi/热点使用与192.168.10.0/24不同的网段，避免两个接口路由重叠；仅换一个192.168.10.x地址不能解决这个冲突。下面不修改eth0配置，也不要求重装Pi系统、OpenCV或模型。

### 1.1 网线暂接电脑与Pi，先配置无线

**电脑PowerShell：**

```powershell
ssh orangepi@192.168.10.3
```

**进入Pi SSH终端后：**

```bash
ip -br addr
nmcli device status
sudo nmcli radio wifi on
nmcli device wifi list
sudo nmcli --ask device wifi connect "你的WiFi名称"
ip -br -4 addr
```

按提示输入Wi-Fi密码，不要把密码发到聊天或录像。记下无线接口IPv4，例如`192.168.1.37`；这是例子，不是要求设置的地址。接口可能不叫wlan0，以实际输出为准。若没有无线接口或nmcli不可用，先保留这两条查询输出，不执行重置全网配置的命令。

**另开电脑PowerShell，用实际无线IP先试登录：**

```powershell
ssh orangepi@192.168.1.37
```

确认这次无线SSH可用，才把Pi的网线改接FPGA。无线SSH应继续可用。若Wi-Fi无法互访，检查是否是访客网络/热点客户端隔离；仅仅显示“已连同一Wi-Fi”不等于互相可达。没有无线条件时，可用已有交换机让三方处于同一有线网；单网口、单网线来回换接不能实现同时在线。

### 1.2 复用已有视觉服务，不开第二个摄像头进程

**Pi SSH终端：**

```bash
cd /home/orangepi/acg720_vision
python3 -c "import json; m=json.load(open('manifest.json')); print(m.get('client_bundle_version'), m.get('bundle_revision'))"
sh tools/start_fpga_follow.sh --status
```

原先的临时拍照程序若仍在前台，先在其终端Ctrl+C退出。需要加载已更新代码或服务未运行时，再执行：

```bash
sh tools/start_fpga_follow.sh --restart
sh tools/start_fpga_follow.sh --status
pgrep -af '[/]pc/usb_gimbal.py'
ss -lntup | grep -E ':8080\b|:6102\b'
tail -n 40 follow-console.log
ip route get 192.168.10.2
```

检查：只有一个实际usb_gimbal进程；服务若已安装应为`active (running)`；启动后端为FPGA UDP/standalone；8080和6102由该进程使用；到192.168.10.2的路由是eth0、源地址192.168.10.3。启动时显示`outputs disabled`是尚未开启输出，不等于视觉服务失败。脚本检查通过仅说明进程启动，不证明FPGA已经收到目标。

若出现`set: Illegal option -`，这是旧包Shell换行问题，在Pi执行一次再重启：

```bash
python3 -c "from pathlib import Path; [p.write_bytes(p.read_bytes().replace(b'\r\n', b'\n')) for p in Path('tools').glob('*.sh')]"
sh tools/start_fpga_follow.sh --restart
```

若出现`Address already in use`，保留`ss`和`pgrep`输出排查进程，不再叠加nohup。若出现`Network is unreachable`，核对发生时的路由和网线，不靠重新选目标解决。若`PI LINK WAIT`，先确认服务、路由和FPGA供电，再按一次题5/6，记录双方状态。

### 1.3 电脑打开识别画面：现有代码已经支持，不需要改Python

当前HTTP仅监听Pi本机127.0.0.1:8080；程序会拒绝`--host 0.0.0.0`。因此这里通过无线SSH转发，**不直接访问“Pi无线IP:8080”**。

**电脑另开PowerShell，替换成实际Pi无线IP：**

```powershell
ssh -N -o ExitOnForwardFailure=yes -o ServerAliveInterval=15 -o ServerAliveCountMax=3 -L 127.0.0.1:18080:127.0.0.1:8080 orangepi@192.168.1.37
```

输入密码后没有终端提示正常，保留窗口；Ctrl+C才结束转发。电脑浏览器打开：

- 完整识别、状态与连拍网页：`http://127.0.0.1:18080/`
- **LCD执行跟踪时优先用只看带框视频的入口：**`http://127.0.0.1:18080/stream.mjpg`

第二个入口没有网页控制按钮和页面脚本，避免操作LCD时又用网页改变PWM/跟踪状态。**完整根网页的关闭、刷新或跳转会发送关PWM指令，即使standalone也如此。** 所以先结束完整网页，再从LCD启动跟踪；跟踪过程中直接打开只读流，不先经过根网页。浏览器看到的是Pi画面；**当前FPGA LCD不接收Pi视频**。这次不需要换屏或把视频搬进FPGA。无线暂时卡顿时先区分“电脑预览延迟”和“Pi识别/FPGA控制延迟”。

若电脑提示本地18080被占用，把命令左侧改为18081，浏览器也改18081，右侧Pi8080保持。网页打不开时，在Pi检查8080监听和`tail`日志；SSH隧道存在不代表相机服务存在。

## 2. Pi按“识别 → 单独云台跟踪 → 搜索 → 接近”测试

1. **识别，底盘停车。** 先打开完整网页，不点PWM/跟踪。让一个人进入视野，检查画面、类别、人脸框、置信度与刷新是否正常；再换小狗。固定一个光照、距离和背景，先录20秒。没有框时只查相机、光照、模型/日志，不先查雷达。
2. **单独云台跟踪。** 切到只看视频入口，LCD→题5→`TRACK FACE`。人缓慢左右移动，再上下移动。应当先准备工作姿态，再跟随，底盘保持静止。记录“有框但不转”“转反”“丢框”“到限位”中的哪一种；这些对应不同问题。人脸稳定后才试`TRACK DOG`。
3. **确认135°。** 状态日志的`FOLLOW runtime:`/`FOLLOW prepared:`应包含135°请求、实际加载的标定、PWM和90°下限。日志是指令估计，不是舵机实测反馈；用侧面照片/量角器核对机械姿态。仍为45°时保存日志和`config/gimbal.json`，不要在多处同时改PWM、角度和图像翻转。
4. **先建立车头参考，再搜索，暂不接近。** 停车，让人站在车头正前方，`TRACK FACE`居中；进入题6，若切页清除了目标，人仍保持正前方，用`FIND FACE`重新锁定，再按`CAMERA FRONT`，确认`CAMERA FRONT SET`。它保存车头参考，不重标PWM角度表。然后再试从视野外、云台可搜索区域执行`FIND FACE`，观察扫描和发现；此动作必要时也会请求底盘转动，应先留出实际转动空间。找到后先记录状态，再试`TURN TO FACE`，不能仅靠“框在画面中间”推断车头朝向。
5. **最后才测`GO NEAR FACE`。** 先确保雷达静态/导航测试通过，场内只留一个明确目标。被识别的人或对应物体必须在雷达扫描平面上有可区分回波；脸本身不用降到雷达高度。`WAIT LASER MATCH`/`LASER AMBIGUOUS`属于测距关联，不等于人脸没识别。不要用框大小猜距离来绕过它。

现有队友Pi包是v22修订3，启动脚本、云台基础控制和视觉任务协议与本机相同；主要差别是速度档、人脸保持等四个文件。**无线预览不要求换队友整包。** 先把现有版本跑通并记录，再单独决定是否对照修订3；不在同一轮同时换固件、Pi代码、模型和标定。现场config和模型保留。

## 3. FPGA：LCD可以操作；VOFA负责远程启动和详细诊断

此节以对应新固件满足部署门槛为前提。已有蓝牙串口通信已实现，**不用再开发VOFA协议**：实际串口号沿用原设备（历史为COM8），115200、8N1、FireWater、ASCII命令末尾换行；逐条等`[ACK OK]`再发下一条。四条曲线仍为轮速相关值，不是XY轨迹。ACK代表受理，不代表到达或路径可行。

### 3.1 第一轮：只停车建图和检查传感器，不急着移动

1. 地面贴O点和+X线，O是**两驱动轮中点**；+Y是车左。摆正车，保持静止让陀螺仪校准。记录位流文件、SHA、源码版本；只在新一轮开始定义原点。
2. LCD→题4`XY NAVIGATION`→`HERE IS ZERO`。它把此刻O设为(0,0)、车头设为世界+X，清旧地图并重置目标为(300,0)。它不是雷达安装朝向标定。
3. HOME→题3`LIDAR AVOID`→`VIEW MAP`。进入题3/4会启用扫描，**看图不需要按START；题3START会让车直行**。
4. 新地图左边全局8.192m，右边局部4.096m；`FIELD / CAR`只切局部窗口中心。灰=UNKNOWN，白=FREE，青绿/深色=不同占据强度。4m橙框是世界参考框，不是自动检测出的场地墙；场地中心假定为世界原点。
5. 放一块在雷达高度可见的纸箱/平板，记录其最近面的实际位置。先放车前约600mm，再换左、右，对照地图、方向扇区距离和有效点计数；远靶不一定产生新的停车触发点记录。只有真发生近障/接触/前瞻停车时，才结合当前flags与trigger_scan_id核对触发XY。已知外参仍为R=(33,-77)mm；O到车体前/后/左右232/118/119/119mm。不要凭跳变改测距比例或扩大SELF。默认ZERO90°并非已实测；方向明显不符时先保存证据，只在停车状态按实物朝向核对`RADAR +90`，每改一次都会清图。
6. 导出5条静态诊断并拍FIELD/CAR地图。在原点两种ROI可能完全相同，此时只确认切换标签；后续安全移动后再沿用同一原点补拍CAR随车照片，不CLEAR。**整圈扫完只证明完成扫描，不能证明每个需要经过的区域都有可靠FREE证据。** 无回波、SELF遮挡和零质量不应当自动变白。

### 3.2 诊断怎么导出（对应新固件才支持操作10）

先在VOFA断开串口；同一COM口不能同时给VOFA和Python。**电脑PowerShell：**

```powershell
cd D:\GOWIN_PROJECTS\acg720_vision_robot
python tools/read_robot_diagnostics.py --port COM8 --count 5 --interval 1 --output dataset/field_20261103/static.jsonl
```

COM8替换成当前已配对串口。只在提示缺少`serial`时，用同一个Python执行`python -m pip install pyserial`。该工具仅发操作10，读快照；不发运动、原点、PID或清故障命令。它没有替你启动导航。

导航连续记录建议：电脑关闭VOFA后运行下面命令，再用LCD发起任务；操作者离开扫描面。

```powershell
python tools/read_robot_diagnostics.py --port COM8 --count 60 --interval 1 --output dataset/field_20261103/nav300.jsonl
```

若使用VOFA发起GO，则等GO的ACK后断开串口、再运行采集工具，会缺少切换期间的数据；需要完整起步记录时用“Python采集+LCD启动”。采集结束后才能重新连接VOFA。60条约覆盖一分钟；等待更久可加大count或另名续采，**日志采集结束不代表车辆任务结束，也不会停车**。没有ACK/协议头不匹配时先查位流版本和串口，不继续发运动命令。

应看这些字段：`reason`、四种状态/错误码、gyro校准/新鲜度、三层lidar ready、scan_id/integrated_id、scan period/age、work_bad、有效/无效点、overrun、四方向计数/采样可见性、front/rear/turn/contact、最近触发raw角度/距离/quality/XY、地图模式和首个拒绝格。

静态健康标准：完整scan_id持续增长，地图integrated_id随新扫描推进；gyro校准完成且新鲜；无新增overrun/解析错误，当前work_bad=false。**这些通过仍不代表路线已知或没有障碍。** 快照为低频记录而非全局原子采样；`mixed_epoch=true`时补采几条，并同时看当前标志与触发scan id，不能把上次触发点当成仍存在的障碍。

| 屏幕/诊断原因 | 下一步只做什么 |
| --- | --- |
| SCAN NOT READY / EXPIRED | 检查完整scan id、年龄、C1供电/接线；不是先改安全距离 |
| GYRO NOT READY / EXPIRED | 停车确认校准和更新，记录gyro标志；不用改编码器比例 |
| LIDAR OVERRUN | 保存计数和当前版本，属于处理健康问题 |
| MEASURE UNKNOWN | 看所需方向、有效点/采样可见性；缺观测不等于发现障碍，也不能强刷FREE |
| NEAR OBSTACLE / VIRTUAL CONTACT | 看当前标志与raw角距quality、车体系XY，和实物位置比较；检查是否确为自身回波，不能直接扩SELF |
| MAP NOT WORLD / WAIT INTEGRATE | 核对pose/heading、地图模式、新扫描是否真正积分；不按固定秒数猜就绪 |
| START UNKNOWN / OCCUPIED | 保留first reject细格、状态、phase，定位真实起点或连接区域；不再按GO十次 |
| GOAL UNKNOWN / OCCUPIED / NO KNOWN ROUTE | 对照目标区域及通路；照片看起来空旷不能代替已观测的FREE |

方向校核与安装细节见[完整诊断文档](雷达避障诊断与起点连接_20261103.md)。若必需空间因固定遮挡一直无法观测，应记录为建模/覆盖问题交回修复，不反复等扫描或删保护。

### 3.3 第二轮：300mm导航，先不放动态障碍

原点已建立且车没有挪动时不再重复归零。**VOFA逐行发送：**

```text
#402,9,0,1,300
#403,9,0,2,0
#404,9,0,3,0
```

三条分别设GX=300mm、GY=0mm、GO。若是新的一轮、需要重新建立原点，先单独发送`#401,9,0,0,0`，等ACK并让新地图获得有效积分，再设目标和GO。操作9会自动切到对应题目页，不需要先ARM。始终使用不同sequence便于对应ACK。

**LCD等价操作：** 题4→`SET GOAL`→按`STEP`选10/100/500mm步长，用X-/X+/Y-/Y+把GX/GY改成300/0→`DONE`→`GO TO GOAL`。读屏确认目标数值后再GO。为防按键操作者遮挡，远程VOFA GO更方便；若从LCD开始，按下后退出扫描平面。

一次只记录：起步能否受理；是否等待/拒绝及准确原因；X/Y/YAW；到达后实际O的位置。用尺量O相对地面标记的XY，并记录测量方法和误差，不用车头边缘代替O；车头距O约232mm，转5°自身就横移约20mm。

300mm可重复完成后，再把目标X改为1000，Y仍为0，再GO。1000是**原坐标系的绝对目标**，不是从当前位置额外前进1m。暂时不要同时测试Y轴、搜索和动态障碍；先确认一条直线。

**导航中留在题4。切HOME、MAP或其他页面会取消任务；不是后台继续导航。** 到达/人工STOP之后才看地图。当前图能画车、目标、当前轴向导航段；不显示完整BFS折线或历史轨迹，不能把这项当作已实现。

### 3.4 第三轮：停车避障 → 原目标恢复

1. 先用题3单独低速验证：停车建图正常后，在雷达高度可见的纸箱前执行`START`（5 COUNT/10ms直行），观察减速/停车，按STOP结束。它不是定点规划，不能用它证明绕障成功。
2. 再从清楚的起点给(1000,0)导航。先用纸箱代替人，在前方保留可停车距离的位置设置障碍；不要把行驶中突然拔线/人贴近车头作为首测。
3. 遇障时录LCD准确原因与日志；检查scan_id、integrated_id继续推进。按用户11月3日晚的新要求，后续修订在同长可行路线中优先左绕；左侧未知或占用时仍选择其他可行路线。15:23旧候选尚不包含这项左绕修改。
4. 如果车辆停车等待，**不要点STOP、切页或重设原点**。移开纸箱，观察后续有效射线清除旧占据、新地图积分推动原目标重规划。恢复不承诺“物体一移开同一瞬间启动”，要有扫描、清图和可行路线证据。
5. 另做一轮：等待中人工按STOP，再移开纸箱；旧任务应保持取消，不自行续走。普通受阻等待与人工取消必须分开验证。真实硬件故障需要处理后重新启动，不要求自动清除。

题3START若一开始因传感器未就绪被拒，需就绪后重按；普通前障门控可能自动恢复，STOP/离页/传感器过期进入停止后则不能假定会自动重发START。连续任务恢复的主验收在题4完成。
