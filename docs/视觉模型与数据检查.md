# 视觉模型与数据检查

检查日期：2026-10-04。本文记录队友发来的资料是什么，以及下一步怎样接到目前的 FPGA＋香橙派工程里。

**先说结论：人脸部分已经跑过检测测试，小狗部分已经有标注；这两份资料里都没有发现训练好的模型文件。**
本次只读取资料和原始照片，没有运行队友的程序，没有训练模型，也没有改动照片或标签。

## 1. “人脸识别”需要先分清三个功能

| 功能 | 可以做什么 | 当前是否已经具备 |
|---|---|---|
| 人脸检测 | 在一张图里找到脸，画框和五个关键点 | 队友已提供离线检测结果；尚未接入我们的实时查看器 |
| 身份识别 | 判断这是 Vera、队友还是陌生人 | 尚未提供身份特征库或对应测试 |
| 目标跟踪 | 选中一个人，连续跟踪，遮挡或交叉时尽量不换人 | 当前 UI 只有选择意图，没有实际跟踪算法 |

预训练人脸检测器可以检测我们三个人，不需要先把三个人各拍 150 张再训练。
但“检测到了两张脸”不等于“知道各是谁”，也不等于“小车能够可靠地跟着指定的人走”。
因此第一步先实现实时人脸框，第二步再实现双击选中和目标关联，第三步才考虑身份识别与电机控制。

## 2. 小狗资料到底是什么

队友提供的文件夹叫 `dog_plush_annotations2`。

| 文件 | 数量或内容 |
|---|---|
| `labels/train/*.txt` | 109 个标签文件，每个文件一个小狗框 |
| `data.yaml` | 唯一类别为 `0: dog_plush`；只定义了训练集 |
| `train.txt` | 列出 120 张图片的路径 |
| 原始图片 | 这份标注包里没有，需要配上我们本机的 PNG |
| `.pt`、`.onnx`、`.rknn` | 没有发现 |
| 训练日志、验证指标 | 没有发现 |

这些 TXT 是 YOLO 检测标注：每行依次是“类别、中心横坐标、中心纵坐标、宽、高”，坐标均相对图片尺寸归一化。
109 个框的格式、类别 ID 和坐标范围都有效，框没有越过图片边界。
抽查原图时，小狗框的位置合理；这不代表已经逐张完成标注质量验收。

本工程已有干净原图，以下路径均相对工程根目录：

```text
dataset/captures/20261003_212720_481564/dog_plush/
```

这里共有 **120 张 400×240 PNG**，109 个标签全部能按文件名找到对应原图。
没有发现完全相同文件的重复图片；但连拍的相邻帧仍然非常相似。

另外 11 张没有 TXT：

```text
burst019_000285.png
burst023_000336.png 至 burst023_000345.png
```

这 11 张原图已逐张查看，小狗已经离开画面，所以更像合理的背景负样本，不能直接说成“漏标”。
让队友确认它们确实没有目标后，整理训练集时可以显式生成同名空 TXT，让背景图片保留在训练集里。
不要给没有小狗的图强行画一个框。

现在 `train.txt` 写的是 `data/images/train/...`，这些路径在标注包里不存在；`data.yaml` 也没有验证集。
因此这份包还不能原样拿去训练，需要先整理图片、标签和路径。

## 3. 人脸资料到底是什么

队友提供的文件夹叫 `face`，里面还有一层 `face`。

| 内容 | 数量 |
|---|---|
| 单张检测结果 JPG | 225 张，分辨率 400×240 |
| 连拍总览 JPG | 15 张，分辨率 1300×588 |
| `detections.json` | 225 条图片检测记录 |
| YOLO 人工标签、训练权重、训练日志 | 没有发现 |

JPG 上已经画了绿色人脸框、分数和关键点；总览图明确写着 `YuNet | threshold=0.60`。
JSON 记录的是每张图检测到的框、五个关键点、分数以及推理耗时。
这些资料说明队友**用 YuNet 跑过人脸检测推理**，不能据此说“训练了我们的人脸模型”。

JSON 的检测数量为：175 张输出一张脸，2 张输出两张脸，48 张没有输出人脸。
这里的 48 张不能直接叫“漏检”：抽查总览时，很多图片里人确实离开了画面。
没有逐张人工真值，就不能用这些数量计算准确率或漏检率。

JSON 记录的推理耗时中位数约 7.93ms，但没有记录执行硬件、版本和完整计时方式。
**这个数不能当作香橙派性能，也不能代表从摄像头拍摄到屏幕显示的总延迟。**

预测框有时超出图像边缘，后续显示、裁剪和选择目标时要将坐标限制在图像范围内。
带绿框、分数和关键点的 JPG 适合查看效果，不适合继续作为干净训练输入或身份录入照片。
我们已有原始 PNG：

```text
dataset/captures/20261003_212720_481564/vera/
```

这里有 225 张干净原图。以后需要做身份特征录入，也应从原图或实时原始帧开始。

## 4. 先查香橙派的 OpenCV，不要急着重装

在香橙派终端或已经登录香橙派的 SSH 终端执行：

```bash
python3 -c "import sys, cv2; print('Python:', sys.executable); print('OpenCV:', cv2.__version__); print('cv2:', cv2.__file__); print('FaceDetectorYN:', hasattr(cv2, 'FaceDetectorYN'))"
```

这条命令只检查现有环境，不会安装或删除软件。
把输出保存下来，再决定使用哪一版模型；存在 `FaceDetectorYN` 也不保证每一版 ONNX 都兼容。

队友给出的 [OpenCV Zoo YuNet 官方目录](https://github.com/opencv/opencv_zoo/tree/main/models/face_detection_yunet)可以参考。
当前目录同时提供 `face_detection_yunet_2023mar.onnx` 和 `face_detection_yunet_2026may.onnx`。
官方说明后者是为了 OpenCV 5.x 的 ONNX Runtime 引擎提供动态尺寸而重新导出的版本。
它不是新增加了“识别 Vera 身份”的模型。OpenCV 4.x 与 5.x 的模型选择需按实际版本核对。

当前 [官方 demo.py](https://github.com/opencv/opencv_zoo/blob/main/models/face_detection_yunet/demo.py) 要求 OpenCV≥4.10.0，默认用 2026may 模型；不要仅凭“装了 cv2”就运行最新示例。旧 OpenCV 4.5.4 的 YuNet 输出解析与 2023mar 模型也不匹配，存在 API 不代表兼容。先取得上面的实际版本输出，再锁定测试环境与模型文件名。

先用现有环境做一张干净 PNG 的加载和检测测试。
如果版本不兼容，再选择匹配的官方模型或单独创建测试环境，保留已经能收图的环境。
暂时不要在工作环境里盲目升级 OpenCV、NumPy，也不要同时安装多个互相覆盖的 OpenCV 包。

## 5. 有没有比 YuNet 更好的算法

“更好”要按我们自己的光线、距离、帧率和开发时间比较，不能只按算法名排序。

| 方案 | 对我们的意义 | 现在的优先级 |
|---|---|---|
| YuNet＋OpenCV CPU | 队友已经测过图片，接现有 Python 查看器最直接 | 第一轮先用它 |
| RetinaFace＋RK3588 NPU | 瑞芯微有正式部署例程，适合后续减少 CPU 推理负担 | CPU 方案不够用时再测试 |
| SCRFD | 另一个可比较的人脸检测器，模型尺寸有多种选择 | 后续候选，需要另外核对转换与部署 |
| SFace 身份特征 | 在人脸检测后比较“是不是同一个人” | 需要指定姓名跟随时再加入 |

瑞芯微的 [RetinaFace 官方例程](https://github.com/airockchip/rknn_model_zoo/tree/main/examples/RetinaFace)列出了 RK3588，并提供模型转换和部署说明。
NPU 方案还要匹配 RKNN 工具、运行库和板上驱动，不能直接把任意 ONNX 文件当成 RKNN 文件运行。
目前不为了换算法而重做正在工作的收图环境。

[SCRFD 官方项目](https://github.com/deepinsight/insightface/tree/master/detection/scrfd)提供算法、训练与模型相关资料。
本次没有确认到与 RetinaFace 同样可直接参考的瑞芯微 Model Zoo SCRFD 目录，所以不把它写成现成的香橙派即用方案。
是否适合我们的 RK3588，需要另行验证模型转换、输出解析和实测表现。

如果需要“认出 Vera”，可以参考 [OpenCV Zoo SFace](https://github.com/opencv/opencv_zoo/tree/main/models/face_recognition_sface)。
流程是检测脸、按关键点对齐、提取特征，再和提前录入的本人特征比较。
通常不用重新训练整个身份模型，但需要清晰录入照片、陌生人拒识和我们自己的阈值测试。

## 6. 怎样接到目前的 FPGA 图像流

**继续使用现有完整的 400×240 图像，不从桌面截图，也不从带 UI 字样的预览图做推理。**

```text
FPGA UDP 数据
  → 一个接收器组装完整帧
  → RGB565 转为干净 BGR 图像
  → 最新帧交给推理工作线程
  → 人脸框与检测状态
  → 查看器显示；之后再接目标跟踪
```

已有 `pc/video_stream.py` 负责完整帧组装和像素转换。
官方示例的 `cv.VideoCapture(0)` 打开本机摄像头，不会接收 FPGA 的 UDP 图像，所以不能直接照运行后期待出现我们的画面。
实时检测应接在这一层之后，图像已经是 OpenCV 使用的 BGR 格式。
一个程序统一接收、显示和推理，避免另开第二个 UDP 接收器抢同一个端口。

接收线程不应等待每次推理完成；推理线程每次取最新完整帧，忙时覆盖待处理的旧帧。
这样即使检测速度暂时慢一些，也不会让程序不断积压几秒前的画面。
检测结果应带对应帧的时间和尺寸，旧结果过期后显示“目标丢失/结果过期”。
推理使用干净帧，框和文字只画到显示副本；拍照文件仍保存干净帧。
用户双击位置需要从预览缩放坐标换回原始 400×240 坐标，再选对应的人脸框。

第一版只显示实时检测框和状态，不发送电机运动命令。
之后增加目标关联、遮挡超时、多人交叉测试，验证后才把结果用于小车运动。

## 7. 小狗训练前怎样整理

使用干净 PNG 和同名 TXT，建议最终目录为：

```text
images/train/  images/val/  images/test/
labels/train/  labels/val/  labels/test/
data.yaml
```

当前小狗只有 8 组连拍，不要把同一组 15 张随机拆到训练集和验证集里。
按整个 `burst` 分组划分，尽量让不同距离和摆放方式都覆盖到；另拍一轮不同场景作独立测试会更可靠。
照片数量少时，验证结果会波动，需要如实记录，不把一次高分当成稳定能力。

第一次训练使用已有预训练轻量检测模型做迁移学习，目标先定为“识别这一只小狗玩偶”。
这不等于识别所有狗、所有玩偶，也不需要一开始就收集大量其他物品。
训练在电脑上完成，之后再导出、测试，决定是否转换到 RK3588 NPU。

## 8. 图像预处理现在能确认什么

原始采集元数据里，`filter_state_manual=unknown`，`fpga_profile_manual=unconfirmed`，最近 UI 观测为空。
所以我们知道这些照片是完整接收到的 400×240 图像，但不能证明采集时高斯滤波开关的状态。
不要在报告里直接写“这些照片全部已经经过高斯滤波”。

保留已有照片，补采时记录实际固件和滤波模式。
用同一批场景比较滤波开关后的效果：降噪可能有帮助，也可能让远处小脸和玩偶细节变模糊。
预处理可以迭代，关键是保留版本记录，并让训练和部署看到的图像处理方式一致。
