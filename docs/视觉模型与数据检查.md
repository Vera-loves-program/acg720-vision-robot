## 1. “人脸识别”需要先分清三个功能

| 功能 | 可以做什么 | 当前是否已经具备 |
|---|---|---|
| 人脸检测 | 在一张图里找到脸，画框和五个关键点 | 队友已提供离线检测结果；尚未接入我们的实时查看器 |
| 身份识别 | 判断这是 Vera、队友还是陌生人 | 尚未提供身份特征库或对应测试 |
| 目标跟踪 | 选中一个人，连续跟踪，遮挡或交叉时尽量不换人 | 当前 UI 只有选择意图，没有实际跟踪算法 |

预训练人脸检测器可以检测我们三个人，不需要先把三个人各拍 150 张再训练。
但“检测到了两张脸”不等于“知道各是谁”，也不等于“小车能够可靠地跟着指定的人走”。
因此第一步先实现实时人脸框，第二步再实现双击选中和目标关联，第三步才考虑身份识别与电机控制。


这里共有 **120 张 400×240 PNG**，109 个标签全部能按文件名找到对应原图。
没有发现完全相同文件的重复图片；但连拍的相邻帧仍然非常相似。

另外 11 张没有 TXT：

```text

burst023_000336.png 至 burst023_000345.png
```

这 11 张原图已逐张查看，小狗已经离开画面，所以更像合理的背景负样本，不能直接说成“漏标”。

| 内容 | 数量 |
|---|---|

JPG 上已经画了绿色人脸框、分数和关键点；总览图明确写着 `YuNet | threshold=0.60`。
JSON 记录的是每张图检测到的框、五个关键点、分数以及推理耗时。
这些资料说明队友**用 YuNet 跑过人脸检测推理**，不能据此说“训练了我们的人脸模型”。

JSON 的检测数量为：175 张输出一张脸，2 张输出两张脸，48 张没有输出人脸。
这里的 48 张不能直接叫“漏检”：抽查总览时，很多图片里人确实离开了画面。

JSON 记录的推理耗时中位数约 7.93ms，但没有记录执行硬件、版本和完整计时方式。
**这个数不能当作香橙派性能，也不能代表从摄像头拍摄到屏幕显示的总延迟。**

预测框有时超出图像边缘，后续显示、裁剪和选择目标时要将坐标限制在图像范围内。
带绿框、分数和关键点的 JPG 适合查看效果，不适合继续作为干净训练输入或身份录入照片。
我们已有原始 PNG：

```text

```

这里有 225 张干净原图。以后需要做身份特征录入，也应从原图或实时原始帧开始。

## 4. 先查香橙派的 OpenCV，不要急着重装

在香橙派终端或已经登录香橙派的 SSH 终端执行：

```bash
python3 -c "import sys, cv2; print('Python:', sys.executable); print('OpenCV:', cv2.__version__); print('cv2:', cv2.__file__); print('FaceDetectorYN:', hasattr(cv2, 'FaceDetectorYN'))"
```

这条命令只检查现有环境，不会安装或删除软件。
把输出保存下来，再决定使用哪一版模型；存在 `FaceDetectorYN` 也不保证每一版 ONNX 都兼容。

队友给出的 [OpenCV Zoo YuNet 官方目录](https://github.com/opencv/opencv_zoo/tree/main/models/face_detection_yunet)可以参考。
当前目录同时提供 `face_detection_yunet_2023mar.onnx` 和 `face_detection_yunet_2026may.onnx`。
官方说明后者是为了 OpenCV 5.x 的 ONNX Runtime 引擎提供动态尺寸而重新导出的版本。
它不是新增加了“识别 Vera 身份”的模型。OpenCV 4.x 与 5.x 的模型选择需按实际版本核对。

当前 [官方 demo.py](https://github.com/opencv/opencv_zoo/blob/main/models/face_detection_yunet/demo.py) 要求 OpenCV≥4.10.0，默认用 2026may 模型；不要仅凭“装了 cv2”就运行最新示例。旧 OpenCV 4.5.4 的 YuNet 输出解析与 2023mar 模型也不匹配，存在 API 不代表兼容。先取得上面的实际版本输出，再锁定测试环境与模型文件名。

先用现有环境做一张干净 PNG 的加载和检测测试。
如果版本不兼容，再选择匹配的官方模型或单独创建测试环境，保留已经能收图的环境。
暂时不要在工作环境里盲目升级 OpenCV、NumPy，也不要同时安装多个互相覆盖的 OpenCV 包。

## 5. 有没有比 YuNet 更好的算法

“更好”要按我们自己的光线、距离、帧率和开发时间比较，不能只按算法名排序。

| 方案 | 对我们的意义 | 现在的优先级 |
|---|---|---|
| YuNet＋OpenCV CPU | 队友已经测过图片，接现有 Python 查看器最直接 | 第一轮先用它 |
| RetinaFace＋RK3588 NPU | 瑞芯微有正式部署例程，适合后续减少 CPU 推理负担 | CPU 方案不够用时再测试 |
| SCRFD | 另一个可比较的人脸检测器，模型尺寸有多种选择 | 后续候选，需要另外核对转换与部署 |
| SFace 身份特征 | 在人脸检测后比较“是不是同一个人” | 需要指定姓名跟随时再加入 |

瑞芯微的 [RetinaFace 官方例程](https://github.com/airockchip/rknn_model_zoo/tree/main/examples/RetinaFace)列出了 RK3588，并提供模型转换和部署说明。
NPU 方案还要匹配 RKNN 工具、运行库和板上驱动，不能直接把任意 ONNX 文件当成 RKNN 文件运行。
目前不为了换算法而重做正在工作的收图环境。

[SCRFD 官方项目](https://github.com/deepinsight/insightface/tree/master/detection/scrfd)提供算法、训练与模型相关资料。
本次没有确认到与 RetinaFace 同样可直接参考的瑞芯微 Model Zoo SCRFD 目录，所以不把它写成现成的香橙派即用方案。
是否适合我们的 RK3588，需要另行验证模型转换、输出解析和实测表现。

如果需要“认出 Vera”，可以参考 [OpenCV Zoo SFace](https://github.com/opencv/opencv_zoo/tree/main/models/face_recognition_sface)。
流程是检测脸、按关键点对齐、提取特征，再和提前录入的本人特征比较。
通常不用重新训练整个身份模型，但需要清晰录入照片、陌生人拒识和我们自己的阈值测试。

## 6. 怎样接到目前的 FPGA 图像流

**继续使用现有完整的 400×240 图像，不从桌面截图，也不从带 UI 字样的预览图做推理。**

```text
FPGA UDP 数据
  → 一个接收器组装完整帧
  → RGB565 转为干净 BGR 图像
  → 最新帧交给推理工作线程
  → 人脸框与检测状态
  → 查看器显示；之后再接目标跟踪
```

已有 `pc/video_stream.py` 负责完整帧组装和像素转换。
官方示例的 `cv.VideoCapture(0)` 打开本机摄像头，不会接收 FPGA 的 UDP 图像，所以不能直接照运行后期待出现我们的画面。
实时检测应接在这一层之后，图像已经是 OpenCV 使用的 BGR 格式。
一个程序统一接收、显示和推理，避免另开第二个 UDP 接收器抢同一个端口。

接收线程不应等待每次推理完成；推理线程每次取最新完整帧，忙时覆盖待处理的旧帧。
这样即使检测速度暂时慢一些，也不会让程序不断积压几秒前的画面。
检测结果应带对应帧的时间和尺寸，旧结果过期后显示“目标丢失/结果过期”。
推理使用干净帧，框和文字只画到显示副本；拍照文件仍保存干净帧。
用户双击位置需要从预览缩放坐标换回原始 400×240 坐标，再选对应的人脸框。

第一版只显示实时检测框和状态，不发送电机运动命令。
之后增加目标关联、遮挡超时、多人交叉测试，验证后才把结果用于小车运动。

## 7. 小狗训练前怎样整理

使用干净 PNG 和同名 TXT，建议最终目录为：

```text
images/train/  images/val/  images/test/
labels/train/  labels/val/  labels/test/
data.yaml
```

当前小狗只有 8 组连拍，不要把同一组 15 张随机拆到训练集和验证集里。
按整个 `burst` 分组划分，尽量让不同距离和摆放方式都覆盖到；另拍一轮不同场景作独立测试会更可靠。
照片数量少时，验证结果会波动，需要如实记录，不把一次高分当成稳定能力。

第一次训练使用已有预训练轻量检测模型做迁移学习，目标先定为“识别这一只小狗玩偶”。
这不等于识别所有狗、所有玩偶，也不需要一开始就收集大量其他物品。
训练在电脑上完成，之后再导出、测试，决定是否转换到 RK3588 NPU。

## 8. 图像预处理现在能确认什么

原始采集元数据里，`filter_state_manual=unknown`，`fpga_profile_manual=unconfirmed`，最近 UI 观测为空。
所以我们知道这些照片是完整接收到的 400×240 图像，但不能证明采集时高斯滤波开关的状态。
不要在报告里直接写“这些照片全部已经经过高斯滤波”。

保留已有照片，补采时记录实际固件和滤波模式。
用同一批场景比较滤波开关后的效果：降噪可能有帮助，也可能让远处小脸和玩偶细节变模糊。
预处理可以迭代，关键是保留版本记录，并让训练和部署看到的图像处理方式一致。

## 11. 模型、训练和几个文件格式是什么意思

| 名词 | 在本工程里的意思 |
|---|---|
| 神经网络（NN） | 按一定结构进行大量计算的模型，其中有可以学习的参数 |
| 训练 | 让模型看图片和正确的框，调整参数；主要在电脑上做 |
| 迁移学习/微调 | 从别人训练过的模型开始，让它继续学习我们的玩偶，不从零训练 |
| 推理 | 用训练好的参数处理一张新图，输出框和分数；香橙派主要做这个 |
| 权重 | 模型学到的参数。模型文件要和加载程序、网络结构配套 |
| `.pt` | PyTorch 模型或训练检查点；可用于继续训练和导出 |
| `.onnx` | 用于跨框架部署的模型格式；要配合正确的推理引擎与后处理 |
| `.rknn` | 转换为瑞芯微部署格式的模型；配合对应芯片、运行库和驱动使用 |
| CPU / NPU | CPU 执行通用程序；NPU 适合加速兼容的神经网络计算。装了 OpenCV 不等于已经用了 NPU |

数据集不需要全部放到香橙派上。电脑保留原图、标签、训练记录；香橙派主要接收实时图像，保存部署模型和少量测试样本。NPU 的量化校准会用到代表性图片，但这不是在香橙派上重新训练。

**本轮选型：YuNet 预训练人脸检测＋YOLOv5n 单类玩偶微调。** 先保留队友已经验证过的人脸路线，暂时不训练我们三个人的人脸模型。

现有标签名称是 `dog_plush`，继续沿用这个名称与类别 `0`，避免整理时改乱。界面显示时可以把它写为 `dog`；把 YuNet 人脸框写为 `human`。这里 `human` 实际代表人脸框，不代表已经加入人体检测或姓名识别。动物狗的预训练类别不能当作已经训练好的这款狗玩偶。

YuNet 是一个独立的人脸检测网络，不属于 YOLOv5 或 YOLOv8；它和玩偶检测器不需要统一版本。二者只需要统一输入图像、坐标和输出字段，就能一起显示和跟踪。

我们选 YOLOv5n，是为了先走轻量模型和已有的 RK3588 部署例程，并不是说 YOLOv5 在所有场景里最好。`n` 是较小的版本；如果远处玩偶的漏检仍较多，在相同数据划分下再比较 `yolov5s`，同时测延迟和资源占用。先跑通一个版本，不并行铺开 v5、v8 多条环境。人脸部分若 CPU 已够用，可以继续使用 CPU，只把玩偶模型迁到 NPU。

### 12.1 先整理数据，再准备训练环境

训练电脑使用我们熟悉的 WSL Ubuntu。香橙派继续保留现在能够收图的环境。先在 WSL 终端查看：

```bash

nvidia-smi
```

第一条应显示 Python 版本；第二条用于检查是否有可用的 NVIDIA GPU。没有这个命令不妨碍 CPU 训练，但不能因此以为 RK3588 的 NPU 能在 WSL 里帮电脑训练。有可用 GPU 时再确认 PyTorch 的 CUDA 版本；没有时可以先跑 CPU，或者让有 GPU 的队友训练。

建议后续训练工作目录是 `~/acg720_training`，不要在 `/mnt/c/Windows/system32` 或香橙派正在使用的 `~/acg720_vision` 中创建训练环境。下面的 `~` 指 **WSL 当前用户的家目录**。

完成整理后，目录应为：

先复制资料并整理，不移动或覆盖现有原图。每张有目标的 PNG 应有同名 TXT；队友确认的背景图使用空 TXT。带检测框的 JPG 不放进训练集。

**现有 8 组连拍必须整组分开。** 可以先试 5 组训练、2 组验证、1 组测试，但应按实际光线和距离检查覆盖情况，不机械地按文件编号切分。现有最后一组含大量背景图，不适合单独承担正样本测试。更好的做法是另外拍一轮新背景、新距离作为测试集，并写下每组的用途。由于本次没有完成具体分组，下面的训练命令目前还不能直接运行。

`nc: 1` 表示一个类别；类别名和现有标签 ID 保持一致。

原来的 `train.txt` 和只含训练集的 `data.yaml` 不直接沿用。按上述实际目录写新的配置即可。[YOLO 标签格式和目录说明](https://docs.ultralytics.com/datasets/detect)

### 12.2 锁定一条能接 RK3588 的软件路线

本方案采用 [Rockchip 的 YOLOv5 导出仓库](https://github.com/airockchip/yolov5)，训练和导出使用同一份源码。官方适配说明写明它基于上游 YOLOv5 **v7.0**，上游基线提交为 `915bbf294bb74c859f0b41f1c23bc395014ea679`。这不是 Rockchip fork 自身的提交号；克隆后还要保存实际提交号，不能只凭“YOLOv5”三个字复现环境。

在 **WSL** 准备独立环境的命令如下。以后执行前应已确认联网和磁盘空间；PyTorch 的下载较大。若 `venv` 提示缺包，先补齐 WSL 的 `python3-venv`，不要改正在收图的环境。

```bash
python3 -m venv ~/.venvs/acg720-train
source ~/.venvs/acg720-train/bin/activate
mkdir -p ~/acg720_training/models
cd ~/acg720_training
git clone https://github.com/airockchip/yolov5.git
cd yolov5
git rev-parse HEAD
```

把最后显示的提交号写入训练记录，之后训练、验证和导出均使用这一份仓库。此处使用仓库内的 `train.py` 等脚本，不使用 YOLOv8 的 `yolo detect train` 命令，也不另装最新 `ultralytics` 来替换它。

下面是一组为这份较旧源码选的初始依赖版本，**本次只核查了源码要求，没有安装或跑过本机训练**。PyTorch 2.5.1 / torchvision 0.20.1 是官方列出的配对版本；选 GPU 构建时还要和本机驱动匹配。

```bash
python -m pip install -i https://mirrors.aliyun.com/pypi/simple/ "torch==2.5.1" "torchvision==0.20.1" "numpy==1.26.4" "opencv-python==4.10.0.84"

python -c "import torch, models.yolo; print('torch:', torch.__version__); print('CUDA:', torch.cuda.is_available()); print('source:', models.yolo.__file__)"
```

最后一条的源码路径应该指向刚克隆的 `yolov5/models/yolo.py`。这些命令只给**训练专用环境**使用，不在香橙派现有系统 Python 中执行。默认 Linux PyTorch 安装可能附带较大的 CUDA 依赖，若只使用 CPU，环境准备时可以再选择对应的 CPU 构建，避免无用下载。CPU 构建的具体地址按 PyTorch 官方页确认，不猜阿里镜像里是否存在该构建。[PyTorch 版本配对](https://pytorch.org/get-started/previous-versions/)、[此仓库依赖定义](https://github.com/airockchip/yolov5/blob/master/requirements.txt)

### 12.3 第一轮训练、验证和看结果

先把官方 v7.0 的 **检测模型** `yolov5n.pt` 放到 `~/acg720_training/models/yolov5n.pt`，不要下载 `yolov5n-seg.pt` 或分类模型。这只是预训练起点，还不是小狗模型。可从 [YOLOv5 v7.0 官方发布页](https://github.com/ultralytics/yolov5/releases/tag/v7.0)取得；不存在该文件时，不要把“路径写好了”当成下载完成。

以下命令都在 **WSL 的训练环境**、已克隆的源码目录中执行，并且要求上一节的数据目录已经整理好：

```bash
source ~/.venvs/acg720-train/bin/activate
cd ~/acg720_training/yolov5
python train.py --weights ../models/yolov5n.pt --data ../dog_plush_dataset/data.yaml --imgsz 320 --epochs 100 --batch-size 8 --device cpu --workers 2 --patience 20 --seed 42 --project ../runs --name dog_plush_v1
```

这是便于先检查流程的 CPU 命令。若 `torch.cuda.is_available()` 为 `True` 且已决定使用 GPU，把 `--device cpu` 改成 `--device 0`。显存或内存不足时先减小 `--batch-size`，不要盲目把图片尺寸降低。100 轮只是第一轮的起点，是否继续训练看验证结果，而不是一定跑满才算完成。

Rockchip fork 对部分结构作过优化，并说明新建网络时会使用 ReLU。读取预训练权重做微调的实际网络与参数应以训练日志和保存模型为准，不能写成“只是改了文件名、结果必然完全一样”。首次使用这份 fork，需要在导出后、部署前做一轮 `.pt` 与适配 ONNX 的同图对照。[官方 fork 修改说明](https://github.com/airockchip/yolov5/blob/master/README_rkopt.md)

完成后检查程序打印的保存目录。首次使用这个名称时通常会出现：

```text
~/acg720_training/runs/dog_plush_v1/weights/best.pt
~/acg720_training/runs/dog_plush_v1/weights/last.pt
```

`best.pt` 是训练程序按验证表现挑出的检查点；`last.pt` 是最后一轮。重复同名运行可能生成新的编号目录，应以实际输出为准，不覆盖第一次记录。

在相同环境中，对独立测试集检查效果，并输出便于肉眼查看的框：

```bash
python val.py --weights ../runs/dog_plush_v1/weights/best.pt --data ../dog_plush_dataset/data.yaml --task test --imgsz 320 --device cpu
python detect.py --weights ../runs/dog_plush_v1/weights/best.pt --source ../dog_plush_dataset/images/test --imgsz 320 --device cpu --project ../runs --name dog_plush_test
```

**loss 下降不等于小车已经会可靠识别。** 它只是训练时的误差指标；模型可能记住了背景。除了看精确率、召回率和 mAP，还要直接看：没有玩偶时是否乱画框，远处是否找得到，遮住一部分时是否还能检测，以及换了房间和光线以后是否失效。测试集太小，分数很容易波动。

第一轮建议单独拍一段没有参与训练的视频，包含“拿入画面→移动→遮挡→拿出画面”，再拍空背景和类似物品。发现错误后记录对应场景并补数据，不只重复拍最容易识别的正面照。[YOLOv5 官方自定义训练说明](https://github.com/ultralytics/yolov5/wiki/Train-Custom-Data)

## 13. CPU 先验收，再转换到 RK3588 NPU

先跑通 PC 离线结果，再在香橙派显示实时框和跟踪，最后再做 NPU。`.pt` 可以先用于电脑验收；板端 CPU 方案可用匹配环境的 PyTorch 或 ONNX 推理。不要为了第一次展示就把完整训练环境装到香橙派。

CPU 版与 NPU 版要共用同一套类别、原图坐标和界面交互。接收线程、推理线程与显示线程分开，推理只取最新完整帧；同一 UDP 端口仍由一个接收器读取。

### 13.1 为什么不能随便导出一个 ONNX 就套官方例程

Rockchip 的 YOLOv5 Model Zoo 明确支持 RK3588，但它的 ONNX 来自修改过的导出源码。输出节点和后处理与普通上游导出不同：部分计算移到 CPU，输出拆成多组。

因此本方案固定使用 **Rockchip YOLOv5 导出仓库＋对应的 yolov5 Model Zoo 后处理**。不能把普通单输出 ONNX 送进要求多组输出的示例，还只修改文件名。也不能拿 YOLOv5 模型套 YOLOv8 的后处理。[官方适配说明](https://github.com/airockchip/rknn_model_zoo/tree/main/examples/yolov5)、[导出修改说明](https://github.com/airockchip/yolov5/blob/master/README_rkopt.md)

### 13.2 导出时确认加载的确实是 Rockchip 源码

以下是**后续导出命令**，只能在上述 Rockchip YOLOv5 fork 的训练环境中使用。安装 ONNX 导出依赖后，检查源码目录和提交号，再执行：

```bash
source ~/.venvs/acg720-train/bin/activate
cd ~/acg720_training/yolov5
python -m pip install -i https://mirrors.aliyun.com/pypi/simple/ "onnx==1.16.2"
git rev-parse HEAD
python export.py --weights ../runs/dog_plush_v1/weights/best.pt --imgsz 320 --batch-size 1 --device cpu --include onnx --opset 12 --rknpu
cp RK_anchors.txt ../models/dog_plush_anchors.txt
```

`--rknpu` 必须明确写在命令中，这是 Rockchip fork 激活适配导出的开关；只修改脚本内默认参数不等价。导出先产生 ONNX，还没有生成最终 `.rknn`。最后复制的 `RK_anchors.txt` 是这份模型的锚框参数，必须和模型一起保存、部署。训练可能重新调整锚框，不能继续用示例的 COCO 默认锚框。[官方导出说明](https://github.com/airockchip/yolov5/blob/master/README_rkopt.md)、[已核查的导出函数](https://github.com/airockchip/yolov5/blob/master/export.py)

导出文件名和输出形状以日志为准。不要随后用普通上游导出覆盖同名适配 ONNX。CPU 的 `.pt` 首先按训练仓库的 `detect.py` 验证；上述多输出 ONNX 按配套 Model Zoo 后处理验证，不能不改后处理就直接替换进普通 `detect.py`。

### 13.3 转换与板端运行还有哪些前提

在电脑的独立转换环境中安装匹配版本的 RKNN-Toolkit2；板端安装与驱动配套的运行库。版本先查后定，不为“最新版”盲目升级香橙派固件。这部分还没有完成环境验证。[RKNN-Toolkit2 官方仓库](https://github.com/airockchip/rknn-toolkit2)

官方 Model Zoo 的 `examples/yolov5/python/convert.py` 支持参数 `ONNX 路径、芯片、精度、输出路径`。在工具环境已准备好的前提下，可先做非量化转换：

```bash
cd ~/acg720_training/rknn_model_zoo/examples/yolov5/python
python convert.py ~/acg720_training/runs/dog_plush_v1/weights/best.onnx rk3588 fp ~/acg720_training/models/dog_plush_fp.rknn
```

这条命令要求 `rknn_model_zoo` 已克隆、RKNN-Toolkit2 可导入、前面的适配 ONNX 实际存在。这里尚没有为你自动建立这些目录或转换环境。

先用同一批测试图比较 `.pt`、适配 ONNX 和浮点 RKNN 的框，再考虑 `i8`。INT8 转换前必须将该脚本默认的 COCO 校准图片列表换成我们的代表性 FPGA 图像列表，覆盖不同背景、光线、距离和空背景。不要拿默认几十张 COCO 图片就声称已完成我们玩偶的校准。[官方转换脚本](https://github.com/airockchip/rknn_model_zoo/blob/main/examples/yolov5/python/convert.py)

板端后处理还要完成以下适配，转换成功不等于已经能实时运行：

- 模型是一个 `dog_plush` 类别，示例原先的 80 类名称、类别数量和 C/C++ 常量需要检查。
- 解码使用随模型导出的 `dog_plush_anchors.txt`。官方 Python 示例有 `--anchors` 参数；C/C++ 的锚框也需改为同一份，不能沿用默认数组。
- 本方案输入为 320×320，示例中的 640×640 尺寸不能原样保留。
- 按比例缩放和补边（letterbox）、BGR/RGB、归一化必须与推理流程配套；检查官方示例的补边值，不凭印象写成另一个值。
- 将输出框正确还原到 400×240 原图，再映射到预览窗口；不能把补边区当作相机图像。
- 正确配套 YOLOv5 多组输出的解码和去重（NMS），再检查 INT8 是否使小目标表现下降。[官方 Python 后处理与锚框入口](https://github.com/airockchip/rknn_model_zoo/blob/main/examples/yolov5/python/yolov5.py)

第一次人脸仍用 YuNet CPU；只有它成为明显瓶颈时，再考虑上一节的 RetinaFace NPU。没有在这块香橙派上实测之前，不承诺“两个模型都达到某个 FPS”。

## 14. 双击选中与再次双击取消，界面怎么做

第一版规则尽量简单：所有检测框都显示 `human` 或 `dog`，选中框用不同颜色。内部目标记录的是“类别＋跟踪 ID”，不是某个固定坐标。

| 操作或状态 | 应有的反馈 |
|---|---|
| 双击一个未选中的框 | 选中该目标，右栏显示类别、ID 和 `TRACKING` |
| 再次双击当前选中的框 | 取消目标，清除高亮；以后接电机时同时取消跟随命令 |
| 双击另一个目标框 | 切换到新目标；旧目标解除选中 |
| 双击空白区域 | 不猜测一个目标，保持当前状态 |
| 点击“取消目标” | 无论当前是否还能看到目标，都可以立即取消 |
| 目标暂时未检测到 | 显示 `LOST` 和丢失时长；以后接电机时先停止，不继续按旧坐标追 |
| 视频中断或结果过期 | 显示连接/检测状态，不把上一张图的框当作当前结果 |

如果两个框重叠，按明确的命中规则选，例如优先较小且包含触点的框；界面要显示选了谁。屏幕缩放和平移时，先把触摸位置换回原图坐标。当前 FPGA LCD 与香橙派查看器是两块独立显示路径，香橙派画出的框不会自动出现在 FPGA LCD 上；要显示在 LCD，后续需增加框坐标回传、帧关联和 FPGA 叠加逻辑。

第一轮建议固定摄像头使用 ByteTrack：它把连续检测框关联为跟踪 ID。人脸检测器和玩偶检测器的结果要明确接入跟踪器，可以先分成两套实例，避免人脸与玩偶互相串 ID。仅对玩偶检测结果运行跟踪器，不会自动把另一个 YuNet 检测器接进去。

ByteTrack 没有外观身份特征，也不做摄像头运动补偿。小车开始移动后再测 BoT-SORT 的运动补偿，必要时增加外观 ReID；同时增加运算负担。无论用哪种方法，都不能保证多人交叉时一定不换人。[跟踪器功能比较](https://docs.ultralytics.com/modes/track)、[ByteTrack 原始项目](https://github.com/FoundationVision/ByteTrack)

跟踪程序需要连续视频帧，不能把不相关照片当成一段视频。YOLOv5 检测输出与 YuNet 输出都要接入跟踪器；本方案不使用 YOLOv8 的 `model.track()` API 来假装它们已经关联。只对同一图像流保留跟踪状态。推理帧率改变时也要检查跟踪超时；小车控制的失效判断用实际经过的时间，不单靠“丢了若干帧”。

以后电机收到的是选定目标的偏移/运动目标及有效时间，不是“看见一张脸就直接给电机 PWM”。视觉框大小也不是准确距离，物理避障仍应使用测距传感器，并由 FPGA 独立判断。

## 15. FPGA 的优势要靠测出来，不靠功能数量

我们可以做一个实用的学习助手，但不能因为用了 FPGA 就说每个功能比 STM32 好。两路电机和几个低速传感器，STM32 通常也能处理；单纯多接几个按钮、音频和 SD 卡不能证明 FPGA 不可替代。

这个项目可以尝试体现的是：多路传感器、编码器、PWM、像素处理同时工作；控制与保护不依赖 Linux 视觉线程按时运行。具体能做到什么，取决于实际 RTL 设计和验证，不能只画在系统框图里。

| 部分 | 本轮适合承担的任务 |
|---|---|
| FPGA | 相机接入与像素处理、视频传输、LCD、本地计时、编码器计数、PWM、固定周期电机控制、测距与超时保护 |
| 香橙派 | 人脸/玩偶检测、目标关联、视觉调试 UI、学习状态规则、语音识别/合成、发送低频运动目标 |
| 云端（可选） | 复杂语言问答和联网服务；不参与本地电机急停与实时避障 |

视频目前已经通过 FPGA，但“经过了一层转发”本身不足以证明优势。若加入高斯滤波、边缘图或缩放，最好同时展示处理效果、吞吐和延迟。神经网络也不是绝对不能放 FPGA 上，但当前先不在这块板上重做 YOLO 加速器；这会增加资源、量化和工具链工作，而香橙派已经有适合的 NPU。

建议保留下面几种测试记录。它们是**拟定的验收方法**，不是已测成绩：

| 测试 | 怎样做 | 记录什么 |
|---|---|---|
| 本地计时 | 正常联网和断网各计时一段；尝试暂停/继续 | 计时误差、提示是否正常、交互是否正确 |
| 视频与检测 | 在同一场景测无检测、YuNet、玩偶、两者同时运行 | 完整帧数、检测次数、漏检/误检、推理耗时、结果年龄 |
| 最新帧机制 | 人为让推理变慢，继续接收视频 | 有没有堆积旧帧、显示是否仍是最近的画面 |
| 选中跟踪 | 移动玩偶或人物，短时遮挡、两人交叉、取消再选择 | ID 是否改变、丢失多久、是否误切目标、取消是否立即生效 |
| 独立保护 | 电机接线与限流确认后，再暂停香橙派程序或断开通信 | FPGA 是否仍响应传感器、是否在设定超时内停车 |
| 控制周期 | 有测量设备后观察控制更新、PWM 和编码器计数 | 周期变化、漏计、保护动作延迟；不用“看起来挺稳”代替数据 |

先给控制周期、通信超时和保护延迟提出目标，再测出实际数值；不要把目标值写成完成值。Python 内推理耗时不等于摄像头到屏幕的端到端延迟；若没有相机时间戳和统一时钟，报告应准确写成“推理耗时”或“从接收完整帧到结果的时间”。

真正可以向老师展示的区别是：**香橙派繁忙、视觉模型慢了或网络断了，FPGA 的计数、控制与保护仍按自己的规则工作。** 若最终只做到了计时和低速电机控制，也应如实说明这是 FPGA 实现练习，不夸成只有 FPGA 才能完成的功能。

## 16. 现在按什么顺序推进

1. 保留已跑通的 FPGA→香橙派收图，记录实际 OpenCV 版本和队友 YuNet 文件名。
2. 先接预训练人脸检测，显示 `human` 框与耗时；不等待三个人的人脸训练。
3. 整理小狗 120 张原图及 109 个标签，确认 11 张背景图，按拍摄批次分组并补一轮独立测试。
4. 确认训练电脑的 CPU/GPU 与磁盘空间，再建立独立训练环境，完成第一轮 YOLOv5n 微调。
5. 接入两个检测器和框选/取消/丢失状态；此时只做视觉跟踪，不让电机移动。
6. CPU 路线有实际测试结果后，再做 RKNN 导出、校准和 NPU 对照测试。
7. 扩展板供电、电平、引脚和电机保护方案确认后，才接入移动控制；录题、联网语音和 SD 听力放到第二阶段。
