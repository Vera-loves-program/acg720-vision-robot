# 数据采集、目标跟踪与 FPGA 视觉交互方案

当前已经验证的基础是：OV5640 摄像头正常显示，电脑成功收到 FPGA 的网络图像。本次增加了可立即使用的连拍工具、主机交互界面，以及供你编译和上板验证的独立 R3 触摸 UI 工程。识别模型、目标跟踪算法和电机跟随尚未接入。

## 1. 香橙派能像 Pocket 那样选中后跟踪吗？

可以实现“点一个人或物体，持续估计它在画面中的位置”。但开发板不会自动具备成熟产品的跟踪效果，需要我们组合检测、跟踪、目标丢失处理和运动控制。

先区分三件事：

| 能力 | 输出 | 是否需要你这 150 张照片 |
|---|---|---|
| 发现画面里有人 | `person` 检测框 | 可以先试已有通用模型，无需先训练你本人 |
| 在几个人里持续跟踪被选中的人 | 被选目标的框、ID、有效/丢失状态 | 可以先用通用检测器加跟踪器；身份保持仍需验证 |
| 确认这个人是 Vera | 身份比对结果 | 与普通人物检测不同，通常另做经过本人同意的人脸登记与特征比对 |

框选物体也可以跟踪。OpenCV 的 KCF 等跟踪器能从初始化矩形开始更新位置，不要求这个物体先属于一个已训练类别。但出现遮挡、离开视野、转身或背景相似时可能漂移。不能把“当前仍有一个框”当成“跟对了目标”。参见 [OpenCV KCF 接口](https://docs.opencv.org/4.x/d2/dff/classcv_1_1TrackerKCF.html)。

推荐后续实现路径：

1. 通用人物检测先跑通，再做小狗玩偶和耳机线的自定义检测。
2. 用户双击时，在点击位置附近选择一个实际检测框；没有检测框时可以进入手动 ROI 初始化模式，并明确显示这一状态。
3. 为选中的目标维护跟踪 ID；跟踪失败时显示 `LOST`，清除运动指令，不能继续追着最后一个位置走。
4. 香橙派输出“目标位置、估计质量、是否丢失、时间戳”；FPGA 完成指令时效判断、传感器避障、编码器闭环和电机控制。

Ultralytics 提供检测结果上的多目标跟踪及 ByteTrack、BoT-SORT 等接口，可作为软件方案参考；它们的 ID 不等于人物身份。部署到 RKNN 时仍需衔接 NPU 推理结果与 CPU 跟踪器，不能假定桌面版的一条 `track()` 命令会自动调用 RK3588 NPU。参见 [官方跟踪文档](https://docs.ultralytics.com/modes/track)。

RK3588 的模型转换与推理参考 [Rockchip RKNN Model Zoo 的 YOLOv8 示例](https://github.com/airockchip/rknn_model_zoo/tree/main/examples/yolov8)。我们可以选择官方已有部署例子的轻量模型作为起点。实际帧率、跟踪稳定性和遮挡恢复效果需要在你的香橙派及摄像头输入上测量，不能按 Pocket 的产品效果作保证。

## 2. 不需要今天永久冻结 FPGA 预处理

需要保持的是**训练与部署的输入约定一致、处理版本可追溯**，而不是以后永远不允许改 FPGA。

当前真实数据链路是：

```text
OV5640：800×480 RGB565
  → FPGA：可开关的 3×3 高斯滤波
  → LCD/DDR：800×480
  → FPGA 网络分支：隔行、隔列取样
  → UDP：400×240 RGB565
  → 电脑/香橙派：转换 RGB/BGR，保存 PNG 或送模型
```

LCD 的英文 UI 是另一条显示叠加路径，不会进入网络照片。电脑端放大、选框和状态文字也不会进入照片。

**建议先把滤波关闭的数据作为一个基线，再采集开启滤波的对照组。** 这不是说 FPGA 不做处理，而是避免未经测试就把有用细节抹掉：高斯可能减少噪声，也可能模糊玩偶纹理、细线和远处小目标。当前高斯窗口是因果窗口，边界两行/两列透传；它不是桌面软件默认边界方式的完全替代。

尤其要先检查耳机线：如果它在收到的 400×240 图像中已经只剩一两像素宽，滤波和二倍取样可能使它断裂或消失。把图片再放大到模型的 640×640 输入无法恢复这些细节。此时应考虑限制展示距离，先识别成团的耳机线/明显接头，或者后续提高网络分辨率，而不是只增加照片数量。

可以按下面的流程决定预处理：

1. 用同一批摆放、距离和光照条件分别采集 `gauss-off-v1`、`gauss-on-v1` 两个 session；切换后等待画面稳定。两组不会是同一时刻的完全配对帧，比较时需要考虑这一点。
2. 各选少量清晰、不同场景的样本先标注，确认目标在输入尺寸上可辨认。
3. 在各自同分布输入上训练/验证；另留固定的实际场景测试集，比较各类召回率、误检和延迟。数据量很小时结果只用于初筛。
4. 有证据表明某个处理改善任务再固定为演示版本；每次改处理、摄像头寄存器或采样方式都升级 profile，并重新验证，必要时补采/重训。

不要强制把所有图像灰度化或二值化。后面的“红色水瓶”等任务要使用颜色，细物体也可能需要保留彩色纹理。可以在 FPGA 内另分出灰度/边缘/颜色候选支路用于统计和 UI 演示，同时继续传彩色图供模型识别。

模型要求的 RGB/BGR 顺序、缩放、letterbox、归一化和 RKNN 量化校准应单独形成一致的软件输入约定。用实际部署来源的代表性图像做量化校准；不能混淆“训练照片”与“量化校准照片”的用途。

本次没有修改已经工作的高斯、摄像头配置、DDR 像素路径或网络降采样参数。拍照工具记录 profile 和人工确认的滤波值。新 R3 还能记录最近观测的实际滤波状态，但遥测与图像没有共同帧号，不能据此保证逐帧精确对应。

## 3. 今天怎样拍这三组照片

完整的终端操作见 [数据采集操作](数据采集操作.md)。你已经能从 WSL 收到 FPGA 视频，所以不需要重新装 Windows Python。

先关闭查看器和收包探测器；同一个 UDP 6102 端口只运行一个接收工具。在 WSL 中进入工程，用之前正常打开视频的 Python 环境运行：

```bash
cd /mnt/d/GOWIN_PROJECTS/acg720_vision_robot
/home/Vera/.venvs/acg720-vision/bin/python pc/capture_dataset.py --bind 192.168.10.3 --fps 3
```

这里使用已经只读确认存在、装有 OpenCV/NumPy 的 WSL 环境，不需要重装。香橙派则使用它自己的 Python 环境，不复制这个电脑虚拟环境。

按 `1` 拍人物，`2` 拍小狗玩偶，`3` 拍耳机线；按空格或 `C` 连拍 5 秒。这里的 `--fps 3` 是最多每秒存 3 张，适合减少相邻重复帧。想多存一些可以用 `--fps 10`。保存速率是上限，缺帧时不会复制旧图凑数。

默认保存位置：`D:\GOWIN_PROJECTS\acg720_vision_robot\dataset\captures`。每次运行创建独立 session，PNG 没有 UI；同时保存 JSON 配置和逐张图片的元数据。

约 150 张/组适合第一轮小场景实验，不能视为通用性能已经有保证。建议每组约 10 次不同条件的 5 秒连拍，然后补拍并筛选，而不是让物体不动、连续存 150 帧。

| 要改变的条件 | 可执行的拍摄安排 |
|---|---|
| 光照 | 日光、台灯、较暗环境、侧光；先保证曝光后仍看得清 |
| 距离与大小 | 近、中、远；特别检查耳机线是否仍有足够像素 |
| 背景 | 桌面、地面、衣服旁、杂物旁；换位置，不把背景当标签 |
| 方向与形态 | 玩偶正侧背面；线材盘起/展开/不同接头方向；人物侧身/坐立/轻遮挡 |
| 同框情况 | 各自单独、两物同时、人与物同时；所有出现的目标都标注 |
| 负样本 | 没有目标的实际背景，以及容易混淆的其他玩偶/普通线材 |

开始可采额外约 10%～20% 的背景/易混淆负样本，这是我们的小规模采集建议，不是模型的硬性比例要求。近似重复帧可以剔除；真正存在的困难场景应保留，避免只挑最容易的照片造成误判。

如果你要训练通用 `person`，自己一个人的照片覆盖不了通用人物外观。可以先保留预训练模型的通用人物能力，再用自己和队友经同意拍摄的实际场景补充；只把三个队员各设一个 YOLO 人物类别容易学到衣服/背景，换衣服不一定还认得。

## 4. 交给队友标注前，先敲定标签规则

推荐第一轮类别：

```text
0 person
1 dog_plush
2 earphone_cable
```

照片按 `vera` 文件夹归类只表示“这组在拍你”，不意味着检测类别一定叫 `vera`。如果决定另外做人物身份识别，把人脸登记样本另行管理，不要混成三个物品检测类别。

小狗玩偶应命名为 `dog_plush`，不能直接假定通用模型的真狗类别等价于这个玩偶。耳机线需要先确定：目标是“整副有线耳机（含线与耳塞）”、还是“散落的某一段线”。建议先选择形态范围明确的整件物品，所有人采用相同的紧包围框规则；细长、折叠、多段线形态更难，必要时再研究分割标注。

标注工具不是 YOLO 本身。可用 CVAT 或其他能导出 YOLO 检测格式的工具。每张图中实际出现几个目标就标几个，不能只标当前文件夹对应的一个物品。确认无目标的负样本保留空标签。YOLO 检测数据配置和标注格式参考 [Ultralytics 检测数据集文档](https://docs.ultralytics.com/datasets/detect)。

训练、验证、测试按**不同拍摄 session、背景、完整连拍组**分开。不要把同一轮连拍相邻照片随机分散到训练集与测试集；这样测到的更像是“见过这个场景”，实际换场景可能失效。第一轮可按场景约 70%/15%/15% 分配，场景太少时先补采，并尽量让每个分组都覆盖三类。

数据分组、场景多样性及独立测试的依据也可参见 [Ultralytics 训练建议](https://docs.ultralytics.com/yolov5/tutorials/tips-for-best-training-results)。上述每组 150 张、采集次数与分配比例是针对你当前原型的安排，不是官方充分数据量承诺。

PNG、session.json 和 metadata.jsonl 一并备份并发给队友。照片目录已加入 `.gitignore`，不会作为普通源码提交。压缩包/队内共享盘保存原始照片，源码 Git 仓库保留代码和处理约定。

## 5. FPGA 的优势怎样实实在在地展示

题目强调 FPGA 实时感知与控制，因此最有力的展示不只是“画面加过一个滤波”。要把系统对确定性、并行性和本地响应的需求放在 FPGA 上。

| 功能 | FPGA 的作用 | 演示与测量方法 | 当前状态 |
|---|---|---|---|
| 摄像头并行采集、跨时钟缓存、LCD 显示 | 摄像头数据进入即处理，显示不依赖 Linux 窗口 | 断开主机程序，LCD 继续显示；测量真实帧率与欠读 | 已有工作链路 |
| 可选高斯与网络降采样 | 行缓存流水线、每个有效像素实时运算 | 开关对照图 + 资源/时序报告；说明细线的利弊 | 已有代码 |
| 触摸坐标读取和手势状态机 | 本地 UI 响应，无需主机处理触摸总线 | 点击/双击/双指操作及事件计数；拔掉网线仍能操作本地状态 | R3 新增，待上板 |
| ROI 裁剪、合理缩放、彩色候选/图像质量统计 | 减少下游数据量、提供可解释的硬件输出 | ROI 字节量、延迟、亮度/饱和/清晰度等真实测量 | 后续候选，未实现 |
| 霍尔编码器计数、PWM、速度闭环 | 多路并行、控制周期可确定 | 转速阶跃响应、控制周期、误差曲线 | 等接线与电机验证 |
| 测距融合、避障、失联保护、物理急停 | 高级算法或通信失效时仍由 FPGA 本地处理 | 中断主机指令、模拟过期/障碍；测本地停车响应 | 等模块方案确认 |

后两项对这次比赛尤其关键。香橙派负责检测、语义和任务规划；FPGA 负责数据采集、关键预处理、最终指令有效性及本地闭环。Linux 卡顿或模型没有输出时，控制链不能无限保持上一条运动指令。

对于图像支路，建议下一项优先做**有帧号和时间戳的可追溯传输**，再做 ROI/图像质量统计。当前 UDP 行协议只有行号，即使严格丢弃残帧，也不能对所有跨帧乱序组合给出证明，更不能测量准确的全链路延迟。R3 UI 遥测序列号不是摄像头帧号。增加共同帧号、处理 profile ID、FPGA 采集时间和实际异常计数，才能让 UI 的性能数字有依据。

别在没有实际计数器时写“FPGA 60FPS、延迟 1ms”，也别在只是完成 PHY 初始化时显示“网线已连接”。资源占用、时序、控制周期和识别性能用实际报告/测量展示。

## 6. 本次已经准备的交互

### 现有 R2 固件 + 新主机脚本

不重新烧录也可以拍照。新版查看器增加侧栏视觉调试、视频双击选点、滚轮 1～4 倍数字预览、取消和恢复视图。选框标注为等待跟踪器，不会自动跟随物体。数字放大不提高源图细节，不影响采集 PNG。

### 新独立 R3 触摸 UI 工程

在 Windows Gowin 打开 `vision_robot_ui.gprj`，顶层 `vision_robot_ui_top`，由你综合/布局布线/烧录 `impl/pnr/vision_robot_ui.fs`。标题应为 `VERA VISION R3`。原 `vision_robot_netfix.gprj` 与 R2 摄像头/DDR/显示文件保持原样。

侧栏操作：

- `VIS DEBUG`：点击切换视觉调试。
- 视频区域双击：记录相机坐标，绘制橙色 ROI 请求框，显示 `ROI PENDING`。它不意味着已经识别人或跟对目标。
- 双指张开/收拢：生成 1×/2× 主机视图请求，LCD 显示 `HOST REQ 1X/2X`。
- `CLEAR ROI`：取消选点；主机查看器收到新计数器时同步取消。
- `CAPTURE 5S`：发拍照事件；运行 `capture_dataset.py` 时触发连拍。若只运行查看器，它提示切换到采集工具，不假报已经保存。

**本次真实放大发生在电脑/香橙派预览，LCD 相机像素仍是 800×480、1×。** LCD 本地数字缩放还需要设计 DDR 区域读地址、行重采样与缓存，不能只改一个 UI 数字或跳过 FIFO 像素，否则会把现有正确画面读乱。因此这次把双指操作与缩放意图接口先准备好，没有把本地缩放宣称为完成。

GT911 驱动、两指坐标与手势代码已实现，但还没有在你的屏幕上验证。启动后先看 `TOUCH OK/TOUCH WAIT/TP ERROR`，测试侧栏点击是否落在正确位置；如果方向不对，按 GT911 文档配置 `SWAP_XY/INVERT_X/INVERT_Y`，不要通过改排线方向解决。

本次核对板卡原理图发现旧触摸约束有误：SDA 应是 **T20**，旧文件误写 **W21**；W21 是以太网 TXD2。R3 使用正确约束，其他触摸脚为 RESET=Y21、SCL=T21、INT=P20。触摸 RESET 是 FPC35，不是 LCD 的 FPC40 RESET。

触摸模块读取真实应答、芯片 ID 和分辨率，保留厂商配置，没有强制覆盖触摸配置表。异常坐标/手掌干扰取消未完成手势，不能被当作正常抬手触发拍照。详见 [GT911 驱动说明](GT911触摸驱动说明.md)。

### 接下来 UI 值得扩展什么

1. **采集页**：拍摄组、剩余连拍时间、实际保存数量、最近样本缩略图、处理版本和丢弃统计；保存数来自主机确认，不能拿 FPGA 请求次数替代。
2. **视觉页**：实际检测框、目标 ID、置信度/质量、`SELECTED/TRACKING/LOST`；模型未运行时灰掉对应字段。
3. **图像调试页**：原图/滤波对照、颜色或边缘候选支路、ROI 范围与字节量、图像质量指标。
4. **控制页**：测距、姿态、编码器转速、期望/实际速度、指令年龄、避障与失联状态；电机未接时显示不可用。
5. **系统页**：FPGA/软件/profile 版本、传感器状态、真正的 PHY 链路状态、传输帧序、统计与错误码。

停止按钮现在只控制协议状态位，项目没有连接电机或实际急停回路，不能称作已经具备紧急制动功能。

## 7. 建议现在的顺序

1. 用现有已工作固件运行拍照脚本，先拍少量样张并确认耳机线可分辨，立即可以做，不等 R3。
2. 拍一小批高斯开/关对照，和队友确认三类定义、框的规则与拍摄分组，再收集各约 150 张。
3. 上板验证 R3 的触摸、坐标方向与遥测；有问题可以直接回到 R2，不改变摄像头链路继续采集。
4. 队友标注期间，我们完成香橙派接收，随后接入通用人物检测及自定义物品模型。
5. 实现明确的跟踪失效处理后，再接入测距/编码器/电机闭环，最后做机器人跟随。

本次 21 项主机检查通过，覆盖完整帧、UDP 本机收发、PNG 色彩/元数据、连拍节奏、坐标映射和遥测乱序。还使用你现有 WSL 的 OpenCV/NumPy 环境实际绘制了普通/放大两种预览并检查排版，原图像素保持不变。鼠标/键盘现场操作、实体触摸和新 R3 上板结果仍需实际确认；FPGA 代码完成静态审阅，按你的要求没有进行编译或仿真。
