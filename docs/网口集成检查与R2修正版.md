## 已找到的错误及修复

### DDR PLL 动态控制没有真正接通

`vision_robot_top.v` 原来把 DDR PLL 的 `pll_init_bypass` 固定接成 0。追踪到 `src/gowin_pll_45/pll_init.v` 的输出选择逻辑后可确定：此时外部 mDRP 操作与写数据被隔断，外部读回恒为 0。这样虽然实例化了 `pll_mDRP_intf`，其输出并没有控制实际 DDR PLL。

R2 先完成 PLL 初始化，采样到初始化结束后的 LOCK 后，将控制权交接锁存为 1，保持到 S0 系统复位。mDRP 控制器和 DDR 控制器在交接完成后才释放复位；没有将 LOCK 直接接到 BYPASS，也没有凭空增加一次停钟脉冲。这符合 [高云时钟资源指南 §5.2.4](https://cdn.gowinsemi.com.cn/UG306E.pdf) 的控制权切换要求。

**限制：旧工程和官方第 45 章同样保留了这个接线隐患。它是确定的接口错误，但暂时不能证明它就是此次新工程黑屏的唯一原因。** 最终需要观察修正后上板的 DDR 状态。

### LCD PLL 初始化倍率不匹配

LCD PLL 的实际参数为输入 50 MHz、IDIV=2、FBDIV=1、MDIV=36，因此 VCO 是 900 MHz，VCO/输入为 18。原初始化模块却传入 `MULTI_FAC=36`，会选择另一组初始化范围。

R2 将初始化倍率改为 18。没有改 LCD 的 45 MHz 输出频率、扫描尺寸或引脚。计算依据是上述源码参数与 [高云时钟资源指南](https://cdn.gowinsemi.com.cn/UG306E.pdf) 的分频关系。

### 高斯滤波及 UI 的组合路径过长

读取用户生成于 2026-10-02 00:25:48 的时序报告，发现真实的同一时钟域问题：

| 路径 | 约束 | 报告结果 |
| --- | --- | --- |
| 摄像头坐标 → 高斯输出像素 | 50 MHz | Fmax 40.791 MHz，最差 setup slack -4.515 ns |
| LCD 扫描计数 → RGB 输出 | 45 MHz | Fmax 40.920 MHz，文字/颜色组合路径过长 |
| UDP 状态机 → 发送 FIFO 的 CEB | 125 MHz | Fmax 104.712 MHz，所列路径数据延迟 9.477 ns |

这些问题不能用总违例数量或跨时钟路径来代替分析，也不能单凭它们断言 DDR 初始化一定失败。

R2 改动：

- 高斯采用同步读行缓存、横向加权、纵向加权输出三级流水线。像素、坐标、有效信号及帧开始标记同步延迟；DDR 写帧复位与网络打包使用延迟后的帧开始信号。
- DVP 坐标是一基数，滤波从 `x>=3、y>=3` 开始，修正原 `x>=2` 导致第二列混入上一行末尾像素的问题。
- UI 分为字符/背景、字形、RGB 合成三级，RGB、DE、HS、VS 同步延迟，保留已经修正的字库方向。
- UDP 发送状态机是单热编码，TX_DATA 恰为 bit 5。FIFO 读请求改用这个状态位，去掉读使能路径上的整字状态比较；没有增加一个会错开首字节的延迟寄存器。

### UDP FIFO 启动长度条件少了 2 字节

每包实际发送 802 字节：2 字节行号 + 400×2 字节像素。原 `eth_tx_ctrl` 却按 `401×2-2=800` 判断可以开始发送。R2 改为等到完整 802 字节。

正常连续采样时，MAC 发包头期间最后两个字节往往能够到齐，因此不能把这个长度问题说成已经证实导致了黑屏或丢包；修正长度条件使启动依据与实际包长度一致。

## 没有发现的错误

静态比对及既有报告显示：原摄像头、LCD、DDR 引脚与 IO 电压约束一致，新增网口引脚没有重叠；DDR PLL 在新旧报告都位于 `PLL_R[1]`，400 MHz 都走 `BANK9_HCLK0`。没有证据说明网口抢占了 DDR 引脚或让 DDR 高速时钟改走普通布线。
